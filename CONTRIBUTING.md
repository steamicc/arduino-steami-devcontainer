# Contribuer

Tout ce qui fabrique l'image est dans `.devcontainer/source/`, qui est aussi le contexte de construction, en local, en CI et à la publication.

## Lancer les tests

Les tests des commandes n'ont pas besoin de l'image : ils utilisent des faux `pio` et `steami-serveur` (`tests/stubs/`). Il faut `bats` (par exemple `sudo apt-get install bats`), Python 3 et Node.

```sh
bats tests/
python3 -m unittest discover -s tests -p 'test_*.py'
node --test tests/*.test.mjs
```

## Construire l'image et lancer le smoke-test

Depuis la racine du dépôt :

```sh
docker build -t steami-devcontainer:dev .devcontainer/source
docker run --rm --network none -u vscode -v "$PWD":/work:ro -w /work \
  steami-devcontainer:dev .devcontainer/smoke-test.sh
```

Le smoke-test vérifie PlatformIO 6.1.19, le paquet STeaMi au tag de l'`ARG STEAMI_PAQUET` du Dockerfile (tag et `version=` de `library.properties`), la compilation du projet d'amorçage, `steami-compiler lis2mdl/basicreader` et celle de tous les exemples listés par `steami-exemples` (au moins 50 ; `STEAMI_SMOKE_EXEMPLES=aucun` saute cette boucle, `tous` par défaut, toute autre valeur fait échouer le test), le firmware DAPLink embarqué (présence, SHA256, `firmware.json`), le tout **sans réseau**, puis zsh comme shell de connexion et l'historique conservé dans `/workspaces` (simulé avec `STEAMI_WORKSPACES`). Le serveur SSH est une feature de `source/devcontainer.json` : seul l'outillage devcontainer (CI) l'applique, `docker build` et le smoke-test ne la voient pas. La première construction télécharge la plateforme, le framework et la toolchain, donc elle est longue. Les tests bats existent aussi dans l'image (`bats` y est installé).

Le workflow `devcontainer.yml` fait la même chose à chaque PR (et à la demande, Actions, « Run workflow »), mais pas sur `main` : `devcontainer-publish` reconstruit et teste l'image au tag. Il est désactivé dans les forks. Ses deux jobs, « tests des commandes » et « build & smoke-test », tournent sur chaque PR, car le ruleset « CI verte avant fusion » les exige. « build & smoke-test » ne construit l'image que si la PR touche une de ses entrées : tout `.devcontainer/` sauf `.devcontainer/devcontainer.json`, `devcontainer.yml`, son filtre `.github/scripts/image-concernee.sh`, `.github/actions/`, `.gitattributes` ou `.gitmodules` (liste et règle dans le script, testées par `tests/image-concernee.bats`). Sinon (docs, tests, autres workflows, PR qui ne change que les deux `devcontainer.json`), il finit vert en quelques secondes avec la notice « construction sautée ». Une PR qui ne change que `devcontainer-publish.yml` prend aussi ce chemin rapide : `devcontainer.yml` ne lance pas ce workflow, il ne peut donc pas le vérifier. Exception : la PR « chore: image » du robot `publier-image` (branche `chore/image-*`) construit toujours, car elle est le dernier contrôle de l'état exact qui va recevoir le tag (le ruleset n'exige pas une branche à jour : deux changements de `.devcontainer/source/`, verts chacun contre un ancien `main`, ne sont construits ensemble qu'à ce moment-là). Dans le doute (liste des changements impossible), il construit. Quand il construit, le chemin de publication (`devcontainers/ci`) passe le smoke-test sans la boucle des exemples (`STEAMI_SMOKE_EXEMPLES=aucun`), et l'étape hors ligne la lance : une seule boucle complète par run.

## Versions figées

Toutes les versions sont exactes, jamais une plage : PlatformIO `6.1.19`, plateforme `ststm32@20.0.0`, framework `platformio/framework-arduinoststm32@4.30100.0` (STM32duino 3.1.0, comme l'Arduino IDE), STM32duinoBLE `1.5.0`, le paquet Arduino STeaMi (`steamicc/arduino-steami`) au tag `ARG STEAMI_PAQUET` du Dockerfile, le firmware DAPLink de la carte (`steamicc/DAPLink`, release `AAAA-MM-JJ.N`, embarqué dans l'image) à la release `ARG STEAMI_DAPLINK_RELEASE` du Dockerfile, avec son SHA256 `ARG STEAMI_DAPLINK_SHA256`, DAP.js `2.3.0` (copie embarquée, sans CDN). Changer l'une d'elles, c'est publier une nouvelle image.

## Publier une nouvelle image

Une version publiée n'est jamais écrasée ni remplacée : les dépôts d'élèves déjà créés pointent dessus. Jamais de tag `latest`.

**Publication automatique.** Il suffit de fusionner sur `main` un changement de l'image, `devcontainer.yml` au vert : tout `.devcontainer/` sauf `.devcontainer/devcontainer.json`, soit `.devcontainer/source/` (le contexte de construction), `.devcontainer/smoke-test.sh` (le test qui décide de la publication) et tout fichier qui y serait ajouté. C'est la règle de `image-concernee.sh` pour `.devcontainer/` (définie une fois dans `IMAGE_CHEMINS` de `.github/scripts/publier-image.sh`, accord vérifié par `tests/publier-image.bats`). Un changement qui n'y touche pas (docs, tests, `.devcontainer/devcontainer.json`, CI) ne donne pas de nouvelle image : les fichiers de CI que `image-concernee.sh` compte en plus (`devcontainer.yml`, `.github/actions/`, le script lui-même) font construire l'image sur la PR, mais n'en changent pas le contenu. Le workflow `publier-image.yml` tourne à chaque push sur `main` (et à la demande depuis `main`, Actions, « Run workflow ») :

1. si l'image a changé depuis le dernier tag `devcontainer-AAAA.MM.N`, il ouvre la PR « chore: image AAAA.MM.N » sur la branche `chore/image-AAAA.MM.N` et active sa fusion automatique (squash) : elle change seulement la version dans `.devcontainer/devcontainer.json` et `exemples/devcontainer.json`, et elle est fusionnée dès que `devcontainer.yml` est au vert. Une seule PR d'image à la fois : si sa PR précédente est encore ouverte, cette PR publiera aussi le nouveau changement. Il met alors sa branche à jour avec `main` (« Update branch », avec le jeton de l'App) dès que `main` a des changements de l'image qu'elle n'a pas : `devcontainer.yml` reconstruit l'image de la PR, ce qui relance aussi une CI tombée en échec. Si la mise à jour échoue, un avertissement le signale, avec la réponse de GitHub, le plus souvent un conflit (le jeton du robot demande la permission Workflows, nécessaire pour pousser une fusion qui apporte des changements de `.github/workflows/`). Mettre alors la branche à jour à la main (« Update branch »). Sinon, si un check exigé de la PR (« tests des commandes », « build & smoke-test ») est en échec, un avertissement, repris dans le résumé du job, signale que la publication est bloquée : relancer les jobs en échec (« Re-run failed jobs »), mettre la branche à jour avec `main` (« Update branch ») si `main` a corrigé la cause (un test, le smoke-test, la CI), ou corriger la PR. Le run de `publier-image` reste vert : ces avertissements sont le seul signal. Il vérifie ensuite sa fusion automatique. S'il existe déjà une branche ou une PR de ce nom (ouverte, fusionnée, ou ouverte par une personne), il ne fait rien. Une PR d'image du robot fermée sans être fusionnée ne bloque pas la publication jusqu'au mois suivant : tant que `main` n'a reçu aucun changement de l'image qu'elle n'avait pas, le robot respecte ce choix (notice « rien à faire ») ; au premier changement de l'image fusionné ensuite sur `main`, il supprime la branche de la PR fermée si elle existe encore (seulement si tous ses commits sont du robot, sinon un avertissement et rien), la recrée depuis `main` et ouvre une nouvelle PR « chore: image AAAA.MM.N », de même version, qui cite la PR fermée. Pour publier sans attendre, suivre « En secours, à la main », point 1 ;
2. au push de la fusion, les deux fichiers citent une version qui n'a pas encore de tag : il vérifie qu'elle n'est pas déjà sur ghcr.io, puis pose le tag `devcontainer-AAAA.MM.N` sur le commit fusionné, avec le jeton de l'App (un tag poussé avec `GITHUB_TOKEN` ne déclencherait aucun workflow) ;
3. ce tag déclenche `devcontainer-publish`, qui construit l'image, refait le smoke-test et ne la publie que s'il passe ;
4. une fois l'image publiée, `devcontainer-publish` lance aussitôt le robot `suivre-image` du modèle `steamicc/arduino-steami-starter` (son cron quotidien reste le secours, et il se lance aussi à la demande), qui ouvre sa PR vers la nouvelle version. Les dépôts d'élèves déjà créés gardent l'ancienne.

La version est `AAAA.MM.N` : le mois courant (UTC), et `N` = 1 + le plus grand `N` des tags du mois, ou 1 pour la première du mois. Elle ne recule jamais : si le mois courant est antérieur à celui du dernier tag, c'est le mois du dernier tag qui sert. Le workflow s'arrête sur une erreur, à corriger par une PR, si les deux fichiers citent des versions différentes, une version qui ne vient pas après le dernier tag, ou une version déjà présente sur ghcr.io sans tag dans ce dépôt. Un échec passager de `publier-image` lui-même ne se corrige pas par une PR : si le run du push de la fusion d'une PR d'image échoue (registre injoignable, push du tag refusé), la PR est fusionnée mais le tag n'est pas posé, et rien ne réessaie avant le push suivant sur `main`. Relancer alors le job (« Re-run jobs ») ou lancer le workflow à la main depuis `main` (Actions, « Run workflow ») : il pose le tag tant que la version citée n'en a pas. Une PR d'image du robot devenue inutile (sa version a déjà un tag) est signalée par un avertissement : la fermer. Pour garder une PR d'image ouverte (fusion à la main), la passer en brouillon ou lui mettre l'étiquette « garder-ouverte » : le robot ne réactive plus sa fusion automatique. Les prérequis sont ceux de `suivre-paquet` (« Mettre à jour le paquet des drivers », « Prérequis, à régler une fois »).

Après chaque publication :

- vérifier que le job `devcontainer-publish` est vert, **y compris l'étape « Post Build, smoke-test & publish »** : c'est elle qui pousse l'image sur ghcr.io, seulement si le smoke-test a réussi. Le robot ne republie pas une version dont la publication a échoué : le tag reste. Après un échec passager (réseau), relancer le job (« Re-run jobs ») ; sinon, la correction suivante de l'image (`.devcontainer/source/` ou `.devcontainer/smoke-test.sh`) prend la version suivante. Si la correction ne touche que la CI (`devcontainer-publish.yml`, `devcontainer.yml`), le robot n'ouvre pas de PR : publier par « En secours, à la main », point 1 ;
- à la première publication seulement, rendre le paquet **public** (Packages, Package settings, Change visibility), faute de quoi les élèves ne peuvent pas le télécharger. Vérifier sans être connecté : `docker pull ghcr.io/steamicc/arduino-steami-devcontainer:AAAA.MM.N`.

Le résumé du job rappelle ces vérifications et signale les configurations qui ne pointent pas encore sur la nouvelle version.

**En secours, à la main** (pour publier sans attendre le robot, ou sans l'App) :

1. Ouvrir une PR « chore: image AAAA.MM.N » qui met la version suivante dans `.devcontainer/devcontainer.json` et `exemples/devcontainer.json` (une version publiée ne change plus et ne se réutilise jamais : prendre la suivante), puis la fusionner, `devcontainer.yml` au vert. À sa fusion, `publier-image` pose le tag de lui-même.
2. Sans le robot (secrets ou App absents), pousser le tag sur le commit fusionné : `git tag devcontainer-AAAA.MM.N && git push origin devcontainer-AAAA.MM.N`. Le workflow `devcontainer-publish` peut aussi être lancé à la main (Actions, « Run workflow ») avec la version en paramètre, une fois présent sur la branche par défaut.
3. Sans le robot du modèle, mettre la nouvelle version dans `.devcontainer/devcontainer.json` de `steamicc/arduino-steami-starter`.

## Mettre à jour le firmware DAPLink

Le firmware DAPLink proposé par la page « Téléverser » est téléchargé à la construction de l'image (`stm32f103xb_steami32_if_crc.bin` de la release `steamicc/DAPLink`), vérifié par SHA256 et copié dans `/opt/steami/flasher/daplink/` avec un `firmware.json` (release, numéro, date `AAAAMMJJ`, taille, SHA256). Il est fixé par `ARG STEAMI_DAPLINK_RELEASE` et `ARG STEAMI_DAPLINK_SHA256` dans `.devcontainer/source/Dockerfile` (seule source : le smoke-test les lit). Le robot `suivre-daplink` (`.github/workflows/suivre-daplink.yml`) épingle **chaque** nouvelle release, sans validation humaine, même une recompilation identique : il est lancé après chaque release par `generate_release.yml` de DAPLink, par son cron quotidien ou à la main (`gh workflow run suivre-daplink.yml`). Il télécharge le fichier, le vérifie contre l'empreinte publiée par GitHub, ouvre la PR `chore/daplink-<release>` (`chore: firmware DAPLink <release>`) et active sa fusion automatique si le ruleset exige les deux checks sans acteur de contournement ; la fusion de cette PR change `.devcontainer/source/`, donc `publier-image` ouvre la PR d'image puis pose le tag. Les PR plus anciennes du robot sont fermées (« Superseded by #n. »). La procédure manuelle ci-dessous ne sert plus qu'à revenir à une release antérieure (le robot ne revient jamais en arrière) : mettre dans les deux `ARG` une release `AAAA-MM-JJ.N` et le SHA256 de son fichier (`curl -fsSL <url> | sha256sum`), puis construire l'image, lancer le smoke-test et fusionner : la publication suit d'elle-même (section précédente). La page compare les releases par date puis par numéro (le `run_number` de GitHub peut repartir de 1) : la date de la nouvelle release doit donc être postérieure ou égale à celle de la précédente.

## Mettre à jour le paquet des drivers

Les drivers viennent du paquet Arduino « STeaMi » (`steamicc/arduino-steami`), le même que celui de l'Arduino IDE, cloné au tag fixé par `ARG STEAMI_PAQUET` dans `.devcontainer/source/Dockerfile` (seule source du tag : le smoke-test et le workflow le lisent). La définition de la carte n'est pas dans le paquet : elle est copiée dans `.devcontainer/source/boards/steami.json` (copiée depuis `boards/steami.json` d'`arduino-steami-lib` v0.30.0, identique jusqu'en v0.34.0 ; la mise à jour automatique ne change que l'`ARG`, donc elle n'est pas rafraîchie toute seule).

**Mise à jour automatique.** Le workflow `suivre-paquet.yml` tourne une fois par jour, à la demande (Actions, « Run workflow ») et après chaque publication du paquet (lancé par `publish-arduino-package.yml` d'`arduino-steami-lib`). Quand `steamicc/arduino-steami` publie une release plus récente que l'`ARG`, il ouvre la PR « chore: paquet arduino-steami vX.Y.Z » sur la branche `chore/paquet-vX.Y.Z` (une seule fois par release : s'il existe déjà une branche ou une PR de ce nom, même fermée, il ne fait rien, sauf vérifier la fusion automatique de sa propre PR encore ouverte, qu'il ferme et recrée depuis `main` si elle est en conflit ; il ferme aussi les PR `chore/paquet-*` plus anciennes du robot, devenues inutiles). Il agit avec le jeton de l'App de l'organisation : `devcontainer.yml` se déclenche sur la PR sans approbation manuelle. Il compare aussi `.devcontainer/source/boards/steami.json` avec celui d'`arduino-steami-lib` au nouveau tag ; s'ils sont identiques, il active la fusion automatique (squash) et la PR est fusionnée dès que `devcontainer.yml` est au vert. Sinon, il le signale dans la PR : reporter les différences (`gh api "repos/steamicc/arduino-steami-lib/contents/boards/steami.json?ref=vX.Y.Z" --jq .content | base64 -d | diff - .devcontainer/source/boards/steami.json`) dans la PR : pour une PR déjà ouverte, il compare la copie de sa branche, donc le passage suivant active la fusion automatique (ou fusionner à la main). Pour garder la PR ouverte, la passer en brouillon ou lui mettre l'étiquette « garder-ouverte » : il ne réactive plus sa fusion automatique. La fusion automatique de `suivre-paquet` et de `suivre-daplink` passe par la garde commune `.github/scripts/garde-fusion-auto.sh`, copiée à l'identique dans les dépôts steamicc : ne pas la modifier ici (`tests/garde-fusion-auto.bats` vérifie son empreinte), mais dans sa source commune, puis la recopier. Elle refuse une PR venue d'un fork ou ouverte par un autre auteur que le robot, exige les deux checks sans contournement possible et, si la fusion automatique est déjà activée et qu'un check exigé est rouge, le relance une fois, puis fait échouer le run du robot s'il reste rouge. Une fois la PR fusionnée, la suite est automatique (« Publier une nouvelle image ») : `publier-image` ouvre la PR « chore: image AAAA.MM.N » et active sa fusion automatique, pose le tag `devcontainer-AAAA.MM.N` à sa fusion, `devcontainer-publish` publie l'image, puis lance le robot `suivre-image` du modèle `steamicc/arduino-steami-starter`, qui ouvre sa PR vers la nouvelle version.

**Prérequis, à régler une fois** (pour `suivre-paquet`, `suivre-daplink` et `publier-image`).

- Les secrets `RELEASE_APP_ID` et `RELEASE_APP_SECRET` (ceux d'`arduino-steami-lib`, dans le dépôt ou l'organisation) et l'App correspondante installée sur ce dépôt, avec Contents et Pull requests en écriture, Actions en écriture pour `suivre-paquet` et `suivre-daplink` (la garde relance un check exigé rouge), et Workflows en écriture pour `publier-image` (mise à jour d'une PR d'image quand `main` a reçu des changements de `.github/workflows/`). Sans les secrets, les workflows échouent en nommant ceux qui manquent.
- « Allow auto-merge » et « Allow squash merging » activés (Settings, General, Pull Requests).
- Un ruleset « CI verte avant fusion » sur `main` qui exige les checks « tests des commandes » et « build & smoke-test », sans acteur de contournement (Settings, Rules, Rulesets, « Require status checks to pass »). Sans lui, la fusion automatique fusionnerait même une CI rouge : les workflows ne l'activent pas, le signalent par un avertissement et laissent la PR à fusionner à la main.

**À la main.** Changer `ARG STEAMI_PAQUET=vX.Y.Z` dans le Dockerfile, puis, si le paquet change de plateforme, de framework ou de dépendance, mettre à jour `.devcontainer/source/amorcage/platformio.ini` et le Dockerfile, à l'exacte. Compiler chaque exemple listé par `steami-exemples` dans l'image construite, puis lancer les tests et le smoke-test en local avant de publier.
